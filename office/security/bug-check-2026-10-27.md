## 1. High: anyone can take over another person's notification settings (SEC-1)
- **Where:** `apps/api/src/drops/notifications/notifications.service.ts:34` (`identify`), route `POST /notifications/identify`.
- **How it fails:** the function returns the stored `subscriberId` for any e-mail address, with no proof of ownership. That id is the only credential for `/notifications/subscriptions` and for push registrations. Proven on localhost earlier: the same id came back for two letter-cases of one made-up address. Still unfixed in develop 6629550.
- **Smallest fix:** never return an existing row for a typed e-mail; insert with `ON CONFLICT DO NOTHING` and otherwise hand back a fresh anonymous id. Patch is ready at `handoff/security-backend/SEC-1-identify.patch`. Add a spec: two calls, two different ids. Owner: Back end.

## 2. High: Railway Postgres password was shown in chat
- **Where:** the hosted Railway database (not in the repo; no Railway credential found in the tree or git history).
- **How it fails:** anyone who saw that chat can connect to the hosted database if its public TCP proxy is still open. I cannot check this from here.
- **Smallest fix:** reset the Postgres password in Railway (Postgres > Variables), update `DATABASE_URL` wherever it is stored, and close the public proxy when the data push is done. Note `.github/workflows/railway-keepalive.yml` says the Railway API app no longer exists; if the database is also unused, delete it. Owner: founder.
- **Label:** Reported.

## 3. High: database and cache are open to the whole network
- **Where:** `docker-compose.yml:7` (`POSTGRES_PASSWORD: postgres`), `:14` (`'55432:5432'`), `:25` (`'6380:6379'`).
- **How it fails:** on this PC, `netstat` shows ports 55432 (Postgres), 6380 (Redis), 4000 (API) and 3000 (web) listening on `0.0.0.0` and `[::]`. Anyone on the same Wi-Fi or LAN who reaches them can log into Postgres as `postgres`/`postgres` and read or change every table, including e-mail addresses and user accounts, and use Redis without a password. Whether Windows Firewall blocks it on the current network profile was not tested. Native Postgres on 5432 is also listening on all interfaces; that one is outside the repo.
- **Smallest fix:** bind to loopback: `127.0.0.1:55432:5432` and `127.0.0.1:6380:6379`; change the dev DB password and set `--requirepass` on Redis (update the `.env` files that use them). Run the API and web dev servers bound to `127.0.0.1` when on public networks. Owner: Back end for compose; founder for the machine.

## 4. Medium: rate limits can be dodged by changing one header
- **Where:** `apps/api/src/common/rate-limit.guard.ts:45` (takes the first `X-Forwarded-For` entry from the request). Same pattern in `apps/web/src/lib/auth/rate-limit.ts` (`clientIp`).
- **How it fails:** on localhost I sent 34 calls to `POST /notifications/subscriptions` with one fixed header value: calls 31 to 34 got 429. With 34 different header values: no 429 at all. Every `@RateLimit` route (waitlist sign-up, feedback, posts, comments, votes, reports, notifications) is therefore unlimited for anyone who sets the header. The waitlist route sends a welcome e-mail, so this is an e-mail-cost and abuse path. On Vercel the web copy is probably safe because Vercel rewrites the header (Unconfirmed); the API's host behaviour is Unconfirmed too.
- **Smallest fix:** in the API use `req.ip` (Express already has `trust proxy` 1 in `main.ts:52`) instead of reading the header; on the web side use the platform's own client-IP header. Owner: Back end.

## 5. Medium: WebSocket accepts oversized frames
- **Where:** `apps/api/src/chat/chat.gateway.ts:56` and `apps/api/src/drops/drop-live.gateway.ts:59` (`@WebSocketGateway({ path })`, no `maxPayload`).
- **How it fails:** the `ws` library's default limit is about 100 MB. On localhost, one anonymous connection to `/ws/chat` sent a 5 MB frame, was not closed, and the server parsed it. A few connections sending large frames can exhaust API memory. In the same file, `chat:join` (`:186`) takes any string as a room id and adds it to an in-memory map with no cap, so room ids can be used to grow memory too.
- **Smallest fix:** `@WebSocketGateway({ path: '/ws/chat', maxPayload: 16 * 1024 })` on both, check `roomId` is a UUID, cap joined rooms per socket (for example 20), and cap connections per IP. Owner: Back end.

## 6. Medium: rotate secrets before launch (SEC-2)
- **Where:** `apps/web/.env.local` (VERCEL_OIDC_TOKEN, AUTH_SECRET, API_JWT_SECRET, TOTP_ENCRYPTION_KEY), `apps/api/.env` (API_JWT_SECRET, RESEND_API_KEY, VAPID_PRIVATE_KEY, affiliate tokens). All git-ignored and never in history (searched all commits).
- **How it fails:** a printed `.env.local` means those values should be treated as exposed. AUTH_SECRET signs web sessions; API_JWT_SECRET signs every API token and is also the shared secret for the internal endpoints, so whoever has it can forge an admin login token for any user id.
- **Smallest fix:** founder rotates VERCEL_OIDC_TOKEN first, then AUTH_SECRET and API_JWT_SECRET (set the same new API_JWT_SECRET on both services; all sessions end, which is fine). Ask Back end before changing TOTP_ENCRYPTION_KEY, because stored 2FA secrets need re-encrypting. Use new values on the host, never the local ones.
- **Label:** Reported (founder-listed). I checked the files are ignored and not committed; I did not read the values.

## 7. Medium: calendar link contains the master watch id (SEC-9)
- **Where:** `apps/api/src/drops/drops.controller.ts:73` (`GET /drops/my.ics?watch=`), link built at `apps/web/src/components/drops/MyDrops.tsx:37`.
- **How it fails:** the same id lets a caller read the feed and change preferences, replace the e-mail or the wishlist. The link is meant to be pasted into other companies' calendar apps. Proven on localhost earlier. Still open.
- **Smallest fix:** a separate random read-only `calendar_token` column for the feed URL, regenerable; add `Cache-Control: private, no-store` on the feed. Owner: Back end and Front end.

## 9. Low: compiled Python files are tracked in git
- **Where:** `scripts/__pycache__/daily_update.cpython-313.pyc`, `scripts/__pycache__/scrape_shopify_prices.cpython-313.pyc`, `scripts/webscraper/__pycache__/core.cpython-313.pyc`, `scripts/webscraper/__pycache__/engines.cpython-313.pyc`. `.gitignore` has no rule for them.

## 10. Low: news feed fetch can hang or exhaust memory
- **Where:** `apps/api/src/scripts/fetch-news-feeds.ts:173` (`fetch(f.url, …)` with no `AbortSignal`, then `await res.text()` with no size cap). Same file calls feeds in a long sequential loop.
- **How it fails:** one feed that stops answering blocks every later feed and the 10-minute news cycle. A hostile or broken feed returning a huge body is read fully into memory.
- **Smallest fix:** `signal: AbortSignal.timeout(20_000)` and refuse bodies above about 2 MB (check `content-length`, read with a limit). The Python image fetchers already cap size at 2 MB and require https; copy that. Owner: Drops and News desk.

## 11. Low: rate-limit counters collide between routes
- **Where:** `apps/api/src/common/rate-limit.guard.ts:50` builds the key from `context.getHandler().name`. Four rate-limited handlers are all named `create`: comments, posts, feedback and reports.
- **How it fails:** a signed-in user's posts, comments and feedback share one counter per IP, so posting, commenting, sending feedback and filing reports all count against one counter per IP, and heavy use of one route locks them out of the others, and the limit numbers in the decorators do not mean what they say.
- **Smallest fix:** key on controller class name plus handler name. Owner: Back end.

## 12. Low: other open items from the first pass

## 15. Low and info: smaller items
- **Sign-up reveals which e-mails have accounts:** `apps/web/src/app/api/auth/sign-up/route.ts:48` returns 409 with the "already exists" message. Reset and login are careful about this; sign-up is not. Fix: accept silently and send a "you already have an account" e-mail, or accept the tradeoff on purpose. Confirmed (code).
- **Password-reset tokens are stored as plain text:** `apps/web/src/app/api/auth/password-reset/request/route.ts:43`. A database read gives account takeover during the 1-hour window. Fix: store a SHA-256 of the token and compare hashes. Confirmed (code).
- **Internal secret compared with `!==`:** `apps/api/src/internal/internal-secret.guard.ts:25`, and it reuses API_JWT_SECRET. Timing attack over the network is hard; the larger risk is one secret doing two jobs. Fix: `timingSafeEqual` and a separate `INTERNAL_SECRET`. Unconfirmed as exploitable.
- **E-mail format check is weak:** sign-up only checks the address contains `@`. Fix: use the same validator as the API. Confirmed (code).
- **Connection URL passed on a command line:** `scripts/push_data_to_railway.ps1:64` builds a `psql "<url>"` command, so the hosted DB password is visible in the process list while it runs, and special characters in the URL can break the `cmd /c` line. Fix: pass it via `PGPASSWORD`/service file. Confirmed (code).
- **Image-fetch scripts can be pointed at internal addresses:** `scripts/fetch_news_images.py`, `scripts/fetch_drop_images.py` accept any `https://` host and follow redirects, so a hostile feed entry could make this PC request an internal https address. Impact is small (https only, size and type checked, nothing returned to the attacker). Unconfirmed.
- **CI:** `.github/workflows/ci.yml` runs `vercel build` with `VERCEL_TOKEN` on every same-repo pull request; forks do not get secrets. Actions are pinned to major versions, not commit hashes. Info.
- **Page-flip** has had no release since May 2022 (info; no advisories).
