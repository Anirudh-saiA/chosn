## Problems
- **Security hole fixed: the rate limiter could be bypassed.** `RateLimitGuard` keyed on the first entry of the `X-Forwarded-For` header, which the caller controls, so a client could send a fresh fake address with every request and never be limited. It now uses `req.ip`; `main.ts` already sets `trust proxy` to 1, so behind one proxy that is the address the proxy saw. Keys now also include the controller name, so two handlers with the same method name no longer share a counter. **Consequence for hosting: the API must sit behind exactly one trusted proxy**, or `trust proxy` must be changed to match. With no proxy, `req.ip` is the socket address, which is also correct. Two proxies in front would be wrong.
- The limiter still **fails open** when Redis is down (existing design). For the mail endpoints that means a Redis outage lifts the cap on sends. Recommendation under Decisions.
- **My mistake, no harm done.** To smoke-test I started the built API on port 4999 with the main checkout's `.env` (not printed). Its background loops started too, and the waitlist drip tried to send a real welcome e-mail through Resend. Resend refused it (the account is still in test mode and only sends to the founder's own address), so **no e-mail left**. I stopped the process after about two minutes; it had also run its schedulers against the local dev DB. Because of this I did not get a live 429 check; the guard is covered by unit tests only. **A locally started API needs `DROP_REMINDERS=off WAITLIST_DRIP=off` and no `RESEND_API_KEY`**; I should have set them.
- The reminder loop and the waitlist drip run inside the API with `setInterval` and **no lock**. Two API instances would send every reminder twice. Fine for one instance; it blocks scaling out (see plan).

**What an API Dockerfile and production compose need**
1. **Dockerfile** (multi-stage, Node 22 alpine, non-root user): `npm ci` for the workspaces, build `apps/api`, copy `dist`, `drizzle/` and production `node_modules`; `CMD node dist/main.js`; a `HEALTHCHECK` on the new `/health/live`. Keep migrations at boot, and add a separate one-shot `migrate` step before a new version starts.
2. **Production compose** (single host): `api` (that image; env from a `.env.production` kept on the host, never committed), `redis` (append-only persistence, not exposed), and optionally `caddy` for TLS. Postgres: **managed is recommended** over a container, for backups.
3. **Media files:** `/media/releases|news|magazine` is read from local disk (`MEDIA_DIR`) and written by the news job. A stateless host needs either a persistent volume shared by the API and the job, or the files moved to the object storage already used for Legit Check photos. Recommendation: object storage. It is the one real code change in the plan; I would own the API side.
4. **Job host:** GitHub Actions scheduled workflows for the nightly prices and the news cycle, each reading `DATABASE_URL` and keys from repository secrets (this is why `dbconn.py` came first). Limits: Actions' minimum schedule is 5 minutes and is best effort, so "every 10 minutes" becomes roughly 10 to 15; and the weekly full scrape (browser-based Puma and Myntra, 1 to 2 hours for Myntra alone) may approach the 6-hour job limit. If it does, that one job wants a small always-on server.
5. **Lock for the in-API loops:** before running more than one API instance, wrap the reminder and drip ticks in a Redis lock (`SET NX EX`), or move them to BullMQ repeatables like the other schedulers. Small change.
6. **Small cleanups:** read `GIT_COMMIT_SHA` as well as `RAILWAY_GIT_COMMIT_SHA`; set `API_PUBLIC_URL`, `WEB_URL`, `WEB_ORIGIN` from the real domain; delete or restore the dead `railway-keepalive.yml`.

**Health endpoint:** `GET /health` already exists (Postgres `SELECT 1`, Redis `PING`, `deployedCommit`), plus `/health/fetch` (price pipeline) and the drop health route. Proposed: (a) a cheap `GET /health/live` that only says the process is up, for the container health check; keep `/health` as readiness. (b) `/health` reuses the shared pool and Redis client instead of opening a new connection on every call. (c) Add job freshness (last nightly import, last news cycle) so a stopped job host shows up; this needs each job to write a heartbeat row, via one additive migration.

**Build order (each step small and tested):** `.env.example` cleanup with dev-safe defaults; Dockerfile, production compose and `/health/live`; Redis lock on the in-API loops; media to object storage; Actions job workflows together with the Data and Desk teams; heartbeat and job freshness. Host choice and cost stay with R&D and the founder.
