====================================================================================================
1. WHAT CHOSN IS TODAY
====================================================================================================
CHOSN is a sneaker price-comparison and release site for India. It reads prices from 9 Indian stores
every night, pairs the same shoe across stores, and shows the cheapest price, delivery, payment
options, a store Trust score, a Buy now / Wait call, a drop calendar and news. It never sells shoes:
it sends people to the store.
Numbers right now (local database): 36,897 shoes, 439,478 shoe-sizes, 1.49 million price records, 9
live stores, 154 drops in the calendar, 138 news items, database size about 2 GB.
Where it runs: only on your PC (Postgres and Redis in Docker, the NestJS API on port 4000, the
Next.js website on port 3002). Nothing is on the internet yet. The nightly update runs from Windows
Task Scheduler at 02:00 on your PC.
Code: GitHub repo Anirudh-saiA/chosn, branch develop. Everything up to the Related-sneakers cards is
pushed. Six later commits (Releases gateway, drops, news, rupees, pictures, extra feeds) are saved
locally and not pushed yet.

4. EVERYTHING NEEDED TO DEPLOY, STEP BY STEP
====================================================================================================
Order matters. Steps marked [NEEDS YOU] need your accounts or money.

Step 1. Decide and buy
----------------------
  - [NEEDS YOU] Domain name (for the site, e-mail sending and the API address). Buy it and keep DNS
    access.
  - [NEEDS YOU] Accounts: hosting for the website, hosting for the API and jobs, a managed Postgres,
    a Redis, an object-storage bucket, Resend, Sentry, PostHog (analytics), a Google Cloud project
    (login and Places). Many have free tiers to start.

Step 2. Hosting layout (recommended)
------------------------------------
  - Website (Next.js): Vercel. The GitHub workflow already has Vercel preview and production jobs;
    they need the VERCEL_TOKEN and project settings.
  - API (NestJS): an always-on server (Railway, Render, Fly.io or a small VPS), NOT serverless,
    because it holds a live WebSocket for drops, a BullMQ job queue, and a scheduler. The old
    Railway address no longer exists and must be replaced.
  - Postgres: managed Postgres (extensions needed: pg_trgm and pgcrypto). Size today about 2 GB and
    growing with price history; plan 10 GB and daily backups. The migrations run on boot (0044 so
    far).
  - Redis: managed Redis for the job queue and rate limits.
  - Nightly scrapers: a small Linux VM or container with Python, Node, Playwright and Chromium, a
    cron entry at 02:00 and a Sunday 01:00 full run. About 40 minutes nightly. Do not use a
    serverless host. Risk: datacentre IP addresses are sometimes blocked by stores; if so, run it
    from a home machine or a residential-IP server.
  - Files: pictures (data/media/releases) and scraped working files (data/...) need a persistent
    disk or an object-storage bucket; the API has a storage service ready for an S3-compatible
    bucket.

Step 3. Configuration (environment variables)
---------------------------------------------
  - Website: NEXT_PUBLIC_API_URL (the API https address), AUTH_SECRET, AUTH_URL, NEXT_PUBLIC_POSTHOG
    key and host, SENTRY_DSN; COMING_SOON=off only when you are ready to open the site.
  - API: DATABASE_URL, REDIS_URL, API_JWT_SECRET, TOTP_ENCRYPTION_KEY, WEB_URL, API_PUBLIC_URL,
    RESEND_API_KEY, RESEND_FROM (an address on your verified domain), RESEND_REPLY_TO, STORAGE_*
    (bucket), VAPID keys for web push, GOOGLE_PLACES_API_KEY (optional), MEDIA_DIR. Do NOT set
    SHOW_DEMO_RELEASES in production.
  - Generate fresh secrets for production; never reuse the local test values.

Step 4. First launch of the data
--------------------------------
  - Run migrations on the empty production database (automatic on API boot).
  - Run the full pipeline once to fill the catalogue (several hours the first time): all stores,
    pairing, import, then the derived tables.
  - Then run, in order: update-fx, track-new-arrivals (first run marks a baseline), compute-outlook-
    priors, log-outlook, fetch-news-feeds, scrape_release_dates + import-drops, fetch_drop_images,
    compute_trust (after business_checks and collect_signals), send-watch-alerts.
  - Import your curated drops and news (data/releases/upcoming.json, news.json) if you want them in
    production; the automatic ones refill nightly.

Step 5. E-mail
--------------
  - [NEEDS YOU] Verify the domain in Resend (DNS records), set RESEND_FROM. Until then waitlist,
    wishlist and confirmation mails do not reach real people. Test each mail type to a real inbox
    and check spam placement.

Step 6. Security and safety
---------------------------
  - HTTPS everywhere; set CORS to the real website address; check the content-security-policy still
    allows pictures from the API (https is already allowed); keep the admin guard; keep rate limits;
    turn on dependency alerts (Dependabot exists).
  - Protect secrets in the host's secret store, not in files; rotate the Resend key that was shared
    earlier.

Step 7. Monitoring and operations
---------------------------------
  - Error tracking (Sentry), uptime check on the API /health (replaces the dead keep-alive), job-
    failure alert mail from the nightly run, a data-freshness check (alert if a store has not
    updated in 36 hours), daily database backup and a tested restore.
  - A short runbook: what to do if a store blocks us, if the nightly run fails, if the database
    fills, how to roll back a bad deploy.

Step 8. Pre-launch checklist
----------------------------
  - Legal pages reviewed; cookie banner and analytics consent working; affiliate disclosure on pages
    with Buy links; privacy page matches what is collected.
  - Mobile check on real phones; slow-network check; accessibility check; search-engine basics
    (sitemap, robots.txt, titles, canonical tags).
  - Remove or hide anything still behind "Coming soon" that is not ready (Community stays closed
    until built).
  - Soft launch to a small group, watch behaviour for a few weeks (what you planned), then buy-in
    marketing and go public.

5. DECISIONS ONLY YOU CAN MAKE
====================================================================================================
  - Hosting choice and budget; domain name.
  - Pictures: keep the current credited pictures, ask permission, or move to official press images.

  - Mobile apps: start as an installable web app; native iOS/Android later only if usage proves it.
  - Who writes editorial content (celebrity, fashion week, global) or which licensed feeds to buy.
  - Whether to add WhatsApp alerts (cost and approval needed).
