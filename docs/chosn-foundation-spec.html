CHOSN Foundation Spec

Sneaker price-intelligence, not a marketplace: CHOSN compares retailer and resale prices and routes users out via "View Deal." This document locks the retailer source list, canonical data model, SKU-matching strategy, and compliance posture that Phase 2 (Days 19–42, price comparison engine) is built against — no application code today.

Status Locked for Phase 2 Region India-first + global resale Date 2026-09-05 Owner anirudhsai356@gmail.com

Assumptions made today — override any of these

01

Region: hybrid — Indian retailers as the primary layer, global resale (StockX/GOAT/Culture Circle) for hype and rare drops.

02

Currency: INR as display currency; native currency stored per snapshot, converted at render — not pre-converted in the DB.

03

Catalog scope: v1 covers 20–30 high-liquidity models, not a full brand catalog — matches the manual-mapping approach in §3.

04

Style code exists for every model in scope — true for Nike/adidas/New Balance/etc., holds across the initial list.

05

Zero scraping of StockX, GOAT, or Nike under any circumstance — partnership or nothing, given enforcement history.

06

Waitlist requires double opt-in (confirmed flag) for deliverability and India data-consent norms — can revert to single opt-in for launch speed.

Section 03

SKU / naming normalization

"Nike Dunk Low Panda" and "Nike Dunk Low Retro White Black 2021" are the same shoe under two retailers' house style. For 20–30 models across 8–10 sources, accuracy beats automation — a manual mapping table is the fastest correct path, not a stopgap.

Canonical key

Every listing resolves to Sneaker.style_code — the code printed on the box and box label (e.g. DD1391-100), near-universal across Nike/adidas/New Balance and already the join key StockX and GOAT use internally. Free-text names never match reliably enough to be the key; style codes do.

Process for the first 20–30 models

1. Seed Sneaker rows by style code — one canonical record per model+colorway, built from brand release info, not retailer copy.
2. For each of the ~10 sources, find that model's actual listing and record a row in RetailerProductMapping: raw title, raw URL, the style code it resolves to.
3. At 30 models × 10 sources that's a ceiling of 300 mappings — small enough to build and verify by hand, seeded from a spreadsheet CHOSN's team maintains directly rather than inferred by a script. Coding the seed loader is Phase 2 work, not today's.
4. mapping_confidence starts at manual for everything; only gets marked verified once a human has confirmed the size run matches too.

Post-v1, not now Fuzzy string matching (brand + model + colorway tokens, regex-extracted style codes from title text) is worth building once the catalog outgrows what a person can map by hand — flagged for Phase 3+, deliberately out of scope while 20–30 models is the whole catalog.

Size normalization

Indian retailers commonly list UK sizing; StockX/GOAT list US. SneakerVariant.size_system records what was actually listed — normalize for display via a small static SizeChart reference table (brand, size_system, size_value, us_equivalent), not by silently rewriting the source size.
